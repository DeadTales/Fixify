# Entrega RF01–RF04

Alcance contrastado con IEEE830_Fixify.pdf, Requerimientos del sistema.pdf y Product_Backlog_y_Requisitos_Sistema_Mantenimiento.pdf. Los documentos se usan como especificaciones del producto.

| Requisito | Backend | Interfaz |
| --- | --- | --- |
| RF01: autenticar personal | Login con contraseña bcrypt, JWT con expiración y rechazo de cuentas inactivas | Validación de campos, errores de conexión y credenciales, contraseña visible opcional y cierre de sesión |
| RF02: restringir por rol | Cada petición protegida consulta la cuenta y el rol actual; un JWT antiguo no conserva permisos retirados | Navegación por rol, sección activa resaltada y administración de usuarios para administrador |
| RF03: registrar clientes | Nombre y teléfono obligatorios, validación de teléfono y correo opcional, confirmación con identificador | Formulario de alta, confirmación y búsqueda en el directorio |
| RF04: registrar equipos | Propietario existente, características y falla obligatorias, rechazo de serie duplicada cuando se proporciona | Selector de cliente, confirmación con identificador EQ y consulta de equipos |

La serie sigue siendo opcional para dispositivos sin número de serie. EQ identifica un equipo; no es el folio de una orden de servicio (RF06).

Las cuentas de técnico acceden al panel inicial; las órdenes asignadas pertenecen a RF05 y posteriores. Los cambios de rol se aplican inmediatamente en la API; la navegación de una sesión abierta se reconstruye al volver a iniciar sesión.

## Validación

- Backend: 17 pruebas con SQLite temporal, incluyendo el consumo del router real por el servicio HTTP del frontend.
- Frontend: 25 pruebas de contratos, servicios, concurrencia, descubrimiento de módulos y enfoque de ventanas.
- Los casos nuevos comprueban serie duplicada, cambio de rol con JWT anterior, desactivación con JWT anterior y registro/búsqueda de clientes con entradas inválidas.

```bash
python -m unittest discover -s backend/tests -v
python -m unittest discover -s frontend/tests -v
```

Para ejecutar la aplicación, instalar backend/requirements.txt y frontend/requirements.txt. En Linux, el frontend también necesita el paquete del sistema python3-tkinter. Configurar backend/DataBase.env y ejecutar el backend desde backend; iniciar frontend/src/app/main.py desde la raíz.

Las pruebas no modifican la base de datos remota. La comprobación de serie duplicada se realiza antes de insertar; para garantizar unicidad frente a altas simultáneas se requiere también una restricción única en PostgreSQL, después de revisar las series existentes.

## Edición y eliminación (05-Oct-2026)

Clientes y equipos admiten edición completa mediante PUT y eliminación mediante DELETE para administrador y recepción. El frontend ofrece ambas acciones sobre la fila seleccionada. No se elimina un cliente con equipos u órdenes, ni un equipo con órdenes; tampoco se cambia el propietario de un equipo con órdenes. Los usuarios se desactivan para conservar historial.

La documentación principal se actualizó añadiendo secciones en los notebooks de backend y frontend, conservando todas sus celdas anteriores. [Guia_Pruebas_Fixify.ipynb](Test/Guia_Pruebas_Fixify.ipynb) explica ejecución por suite, archivo y caso.

## Administración de usuarios

Editar usuario permite cambiar nombre y rol mediante PUT /usuarios/{user_id}; conserva contraseña, estado e ID. Activar/desactivar permanece como PATCH y sustituye la eliminación física para conservar historial. Los botones se muestran sobre la tabla: editar amarillo, desactivar rojo y activar verde.
